# Brief Written Explanation of the System

## What the software does

The Word Pronunciation Reporter is an AI-powered tool that helps people look up English words, see how they are pronounced, and get a short AI-written report they can save. At its core, the software does three things: it talks to a dictionary API to fetch pronunciations and definitions, it gives you a web app to search and browse words, and it uses an AI model (Ollama) to turn that data into a readable summary you can download. In the app you can type any word, pick one from a filterable list (by starting letter or word length), or hit “Random word” to practice. For each word you see phonetic spellings, definitions, and when the API provides it, an audio player so you can hear the pronunciation. You can then save reports in several ways—including a full Word document with the word data plus an AI summary, or the AI report alone in plain text, Markdown, HTML, or Word format—so the same report can be used in different contexts (e.g. sharing, notes, or documentation).

## How the components work together

The system is split into a few main parts that pass data in a clear sequence. The **API client** is responsible for all dictionary lookups: it reads your Merriam-Webster API key from `word.env`, calls the Collegiate Dictionary endpoint with the word and key, and if the key is missing or invalid it falls back to a free dictionary API so the app still works. It returns a single, normalized structure (word, pronunciations, definitions, audio URLs) that the rest of the app relies on. The **Shiny app** is the interface: the sidebar handles the word input, filters (letter and length), random word, and the word-list dropdown, while the main area shows the result card (pronunciations, definitions, audio) and the “Save AI report” section. When you ask to save a report, the app calls the **Ollama client**, which builds a short JSON summary of the word data, sends it to Ollama (either cloud with a key from `ollama.env` or a local Ollama server), and gets back a narrative. The Ollama client also formats that narrative into .txt, .md, .html, and .docx using the same logic as a multi-format reporting pattern (plain text and Markdown as-is, Markdown converted to HTML, and line-by-line parsing for the Word doc). To avoid calling the AI multiple times for the same word, the app caches the latest AI report text per word; the first download for that word triggers Ollama, and any other format reuses the cached text. Standalone scripts (`word_good_query.python.py`, `word_trends.py`, and running `ollama_client.py` from the command line) use the same API client and Ollama client so behavior stays consistent whether you use the app or the command line.

## Design choices and challenges

One important design choice was to support both Merriam-Webster and a fallback API. The assignment asked for use of a specific API key, but keys can be wrong or expired, so the client first tries Merriam-Webster with the key from `word.env`; on a 401 or other auth error it automatically falls back to a free dictionary API and maps that response into the same shape (pronunciations, definitions). That way the app always returns something useful and the user sees a single, consistent structure regardless of which API answered. Another choice was to keep the AI report out of the main screen and only offer it as downloadable files (full .docx or AI-only in .txt, .md, .html, .docx). That keeps the UI simple and makes it clear that the “product” of the AI step is a saved report, not a live panel; it also matched the requirement to save reports in multiple formats. A practical challenge was making sure the first download for a word did not trigger four separate Ollama calls when the user tried .txt, .md, .html, and .docx. To fix that, the app caches the AI report text and the word it was generated for; the first save for that word runs Ollama once and stores the result, and every other format reads from the cache. Clearing that cache when the user looks up a new word avoids serving an old report for a different word. Finally, the word list for “browse and random word” is a built-in list plus optional filtering by letter and length, rather than calling an external API for the list. That keeps the browse feature fast and usable even when the dictionary API is slow or the key is missing, and it gives learners a fixed set of words to practice with without extra network calls.
